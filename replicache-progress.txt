## Task 1: Verify row-version triggers fire on INSERT + UPDATE with distinctness guard

Issues found and fixed:
  1. packages/db/src/migrations/0033_sync_row_version_triggers.sql — `bump_row_version()` had no no-op guard. Combined with `lifecycle_dates.updatedAt` using Drizzle's `$onUpdate(() => new Date())`, every `.update()` call auto-bumps `updated_at`, so even a semantic no-op UPDATE (e.g. momentUpdate called twice with identical payload) would satisfy a vanilla `WHEN (OLD.* IS DISTINCT FROM NEW.*)` clause and bump `row_version`, emitting a redundant `put` on the next CVR diff. Fixed by adding migration 0038_sync_row_version_distinctness_guard.sql which replaces the function with a body-level guard: compare `to_jsonb(NEW) - 'row_version' - 'updated_at'` vs OLD's equivalent, and short-circuit when they're IS NOT DISTINCT FROM. Exclude the metadata columns so Drizzle-generated timestamp bumps don't count as a change. Also updated _journal.json (idx 38) and copied 0037_snapshot.json → 0038_snapshot.json (schema unchanged; new snapshot id + prevId chain).

Issues noted (no fix needed):
  1. packages/db/src/migrations/0033_sync_row_version_triggers.sql:10-22 — Trigger is `BEFORE UPDATE` only (no INSERT). Confirmed intentional and correct: the in-migration comment explains it, and pull.ts step 6 relies on presence-in-current vs presence-in-prev (not row_version) to detect new rows. A new row's row_version defaults to 0, and the CVR diff emits `put` because `prevSnapshot.{table}[id]` is undefined, independent of row_version value. Adding `BEFORE INSERT` would be redundant.
  2. packages/api/src/modules/replicache/pull.ts:141-183 — Pull publishes three entity types: assetMoments, assetComments, notifications. All three schemas have `row_version integer NOT NULL DEFAULT 0` (comments.ts:42-43, moments.ts:54-55, notifications.ts:46) and all three have a bump trigger (0033 for moments/comments, 0037 for notifications). Cross-reference complete — no synced entity is missing a trigger.

Library improvements made:
  - None applicable — the fix is a Postgres trigger function, not a library call. Verified the `to_jsonb(record) - 'col'` pattern is idiomatic (confirmed via mcp__grep__searchGitHub in kuestcom/prediction-market audit trigger).

Checklist verification:
  - BEFORE INSERT OR UPDATE — UPDATE covered by 0033/0037. INSERT deliberately omitted; CVR diff emits puts on presence, not row_version. Design documented in 0033 header comment.
  - No-op UPDATE guard — 0038 adds body-level guard excluding updated_at + row_version. Handles Drizzle $onUpdate auto-bump case where a simple WHEN clause would not.
  - Every synced table has a trigger — assetMoments (0033), assetComments (0033), notifications (0037). All three match the entities emitted by pull.ts.
  - Appropriate data types — rowVersion is integer (not bigint; 2^31 updates per row is effectively infinite for this domain). jsonb body column on notifications uses `.$type<>()`-style narrowing via NotificationType discriminants at the serialization layer (service.ts).
  - Idempotent DDL — 0033 uses CREATE OR REPLACE FUNCTION + DROP TRIGGER IF EXISTS. 0037 does the same. 0038 reuses CREATE OR REPLACE FUNCTION — safe to re-run.

  1. packages/db/src/migrations/0034_asset_invite_role_not_owner.sql:7-9 — `ALTER TABLE ... ADD CONSTRAINT ... CHECK (role IN ('editor','viewer'))` is a plain (validating) constraint add. Postgres takes an ACCESS EXCLUSIVE lock and validates ALL existing rows immediately. In a large-table deploy this could stall writes for the duration. ## Task 6: Audit pull.ts for CVR determinism and per-user visibility filter

Approach: audited pull.ts + cvr.ts + authz.ts against three criteria — (a) non-deterministic sources inside CVR/patch construction, (b) ORDER BY stability on every query whose output order flows into the patch or persisted snapshot, (c) visibility filter correctness for the initial (cold) pull. Grepped for `Date.now|Math.random|new Date(` under modules/replicache/; inspected every `.select()` for ORDER BY; re-read the WHERE clauses against authz.ts.

Issues found and fixed:
  1. packages/api/src/modules/replicache/pull.ts:142-161, 167-184, 276-282 — None of the three hot-path queries (moments, comments, notifications) and the clients LMID query had an ORDER BY. Iteration order of result rows feeds directly into the patch array (`patch.push` in a `for (const m of currentMoments)` loop) AND into the snapshot's insertion order (`nextMoments[m.id] = ...`), which is JSON-serialized and read back on the next pull. Two pulls on identical (cookie, clientGroupID, userID, DB state) could therefore produce different patch array orders, breaking the task's "deterministic output" requirement. The snapshot keyed by id is lookup-insensitive to order, but (a) the patch array order IS observed by Replicache's client-side JSON log / debugger diffs, and (b) `Object.entries(prevSnapshot.moments)` in the del-loops iterates insertion order, which only stays stable if the write side is stable. Fixed by adding `.orderBy(asc(assetMoments.id))`, `.orderBy(asc(assetComments.id))`, `.orderBy(asc(notifications.id))`, and `.orderBy(asc(replicacheClient.id))`. Added `asc` to the drizzle-orm import. A one-line comment in the moments section explains the determinism rationale so future contributors don't drop the ORDER BY as "unnecessary". Verified API signature via `node_modules/.pnpm/drizzle-orm@0.44.7*/node_modules/drizzle-orm/pg-core/query-builders/select.d.ts:527-541` — `.orderBy(...columns)` accepts `asc(col)`/`desc(col)` wrappers exactly as used.
  2. packages/api/src/modules/replicache/pull.ts:247-248 — `value: n as unknown as Record<string, unknown>` is a double-cast through `unknown`, the specific anti-pattern flagged by review-prompt.md TypeScript §2 ("No `as unknown as T`"). Notification is a tagged union with a fixed set of flat + nested-object fields, so a structural serializer is cheap. Fixed by adding `serializeNotification(n: Notification): Record<string, unknown>` alongside the existing `serializeMoment`/`serializeComment` helpers — fresh object literal, no cast, TypeScript widens literal → `Record<string, unknown>` via the fresh-literal rule (same mechanism that makes `serializeMoment`'s return assignable). Fields enumerated explicitly so adding a new Notification type / field forces a compile error here (see isNotificationOfType in types.ts:144 for the discriminant helper).
  3. packages/api/src/modules/replicache/pull.ts:210-214, 242, 264-267 — `nextSnapshot.notifications![n.id]` and `nextSnapshot.notifications![id]` used `!` non-null assertions on an optional field even though `nextSnapshot` was locally initialized with `notifications: {}`. Flagged by review-prompt.md TypeScript §2 ("No unjustified non-null assertions"). `notifications` is optional in `CVRSnapshot` for backwards-compat with pre-deploy Redis snapshots (valid), but the local `!` assertion leaks that concern into every write site. Fixed by refactoring `nextSnapshot` assembly: declare three local `Record<string, ...>` accumulators (`nextMoments`, `nextComments`, `nextNotifications`), populate them in the put-loops, then build `nextSnapshot` once at the end as a single object literal. Same pattern `currentLmids` already used for the clients map — this harmonizes the style. Zero `!` assertions in the final code.

Issues noted (no fix needed):
  1. packages/api/src/modules/replicache/pull.ts:138-184 — Queries inside `db().transaction` are serialized by the underlying pg/postgres-js driver even when wrapped in Promise.all (single connection per tx). `Promise.all` would not speed them up here, would lose the per-query error localization, and would obscure read-order intent. Kept sequential `await`s — correct pattern for the tx-per-pull model.
  2. packages/api/src/modules/replicache/authz.ts:6-12 — `getAccessibleAssetIds` returns assetIds in indeterminate order. That's fed to `inArray(assetMoments.assetId, assetIds)` in the WHERE; Postgres treats IN-list order as irrelevant (sets, not sequences) so result order depends only on the moments query's ORDER BY. The assetIds order leaks nowhere else. No need to sort. Task 8 will re-audit authz.ts for coverage, so leaving the query shape as-is.
  3. packages/api/src/modules/replicache/pull.ts:181-184 — Notifications are NOT filtered by `assetIds`. ## Task 7: Wrap push mutations in a transaction; verify mutation-ID monotonicity

Approach: audited push.ts against the three plan criteria — (a) single outer transaction wrapping LMID reads + mutator writes + LMID advances, (b) duplicate-mutation dedup semantics (<= skip silently), (c) LMID advance on mutator failure so the client rebases rather than re-queuing forever. Cross-referenced the LMID upsert against Drizzle's `setWhere` support and verified nested transactions use savepoints.

Issues found and fixed:
  1. packages/api/src/modules/replicache/push.ts:133-161 (pre-edit) — `handlePush` was NOT wrapped in a single transaction. Each mutation opened its own `db().transaction(...)`, and `getLMID` + the error-path `advanceLMID` ran on the raw pool connection (no tx at all). This created a monotonicity race window: two concurrent pushes from the same clientID could each `getLMID → 5`, both see `mutation.id = 6 > 5`, both enter separate transactions, and the later-to-commit would overwrite the LMID with whatever value it had locally. If two requests arrived in reverse order (push2 with id=7 committed first, push1 with id=6 committed second), the LMID would regress from 7 to 6 — Replicache's client would then re-queue 7, and the server could either dedup or apply twice depending on mutator idempotence. Fixed by wrapping the entire push handler (clientGroup bind, mutation loop, all LMID reads and writes) inside a single `db().transaction(...)` with per-mutation savepoints for isolation. See fixes #2 + #3 below for the monotonicity guard and savepoint strategy.
  2. packages/api/src/modules/replicache/push.ts:53-64, 149-160 (pre-edit) — `advanceLMID`'s `onConflictDoUpdate({ set: { lastMutationId: newId } })` had no monotonicity guard. Even within a single transaction, an out-of-order LMID write would regress the row. Fixed by adding Drizzle's `setWhere: sql\`${replicacheClient.lastMutationId} < ${newId}\`` — the UPDATE only applies when the new id strictly advances the current value. Verified the API in `node_modules/.pnpm/drizzle-orm@0.44.7*/node_modules/drizzle-orm/pg-core/query-builders/insert.d.ts:61-68` (`PgInsertOnConflictDoUpdateConfig.setWhere?: SQL`) — it compiles to a standard Postgres `ON CONFLICT ... DO UPDATE ... WHERE` and keeps the upsert atomic. Unified the single `advanceLMID` helper to take `tx` as its first arg so both the error-path and success-path advances run inside the outer transaction with the monotonicity guard applied consistently.
  3. packages/api/src/modules/replicache/push.ts:133-161 (pre-edit) — No isolation between mutations. With per-mutation transactions, a crash in mutation 3 would roll back only mutation 3. But in a single outer transaction, any throw would roll back ALL prior mutations in the batch — violating Replicache's rebase contract (the client expects mutations with advanced LMIDs to be either applied or explicitly rejected, not silently reverted). Fixed by wrapping each mutator call in a nested `tx.transaction(async (subTx) => { ... })` — Drizzle's nested transaction issues `SAVEPOINT spN` / `ROLLBACK TO SAVEPOINT spN` / `RELEASE SAVEPOINT spN` under the hood (verified in `node_modules/.pnpm/drizzle-orm@0.44.7*/node_modules/drizzle-orm/node-postgres/session.js:206-220`). If a mutator throws, only its writes roll back; the outer tx stays alive, and the subsequent LMID advance commits with the rest of the batch.
  4. packages/api/src/modules/replicache/push.ts:170-184 (pre-edit) — `console.error('mutator crashed', name, err instanceof Error ? err.message : err)`. The fallback branch logs the raw `err` (which is `unknown` from the catch binding). Per review-prompt.md §Common Patterns #1 (real-world finding: `err` can contain connection strings, SQL state, stack traces), changed to `String(err)` for the non-Error path. Same pattern applied to the user-poke catch block at what is now line 227-230.
  5. packages/api/src/modules/replicache/push.ts:75-99 (pre-edit) — ClientGroup bind/create (the trust boundary check) ran on the raw pool connection, outside any transaction. Fixed by moving it inside the outer `db().transaction(...)` so the check and any subsequent LMID writes in this push see consistent state. If the clientGroup creation races another push, `onConflictDoNothing` absorbs the duplicate. Forbidden returns early with a typed discriminant (`{ forbidden: true }`) that escapes the transaction without committing any work.

Issues noted (no fix needed):
  1. packages/api/src/modules/replicache/push.ts:168-172 — The `serverMutators[mutatorName] as (tx, args: unknown, ctx) => Promise<void>` cast cannot be eliminated without a per-mutator switch statement (8 cases). Library improvements made:
